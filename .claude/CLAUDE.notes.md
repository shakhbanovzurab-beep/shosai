## Заметка 1

# Whisperer

## Что такое Whisperer

**Whisperer** — это интеллектуальная AI-платформа (AI Workspace), которая объединяет человека, его знания, встречи, документы, задачи, календарь, коммуникации и искусственный интеллект в единую экосистему. Платформа помогает пользователю сохранять знания, понимать информацию, автоматизировать рутинные процессы и эффективно работать с помощью современных AI-моделей.

Whisperer проектируется как **швейцарский нож**: каждая новая возможность — это не отдельный инструмент, а ещё одно лезвие единой системы. Все функции должны быть тесно интегрированы, использовать общий контекст пользователя, усиливать друг друга и работать как части одного целого, а не как изолированные модули.

Главная цель Whisperer — помочь человеку эффективно работать с информацией, автоматизировать рутинные процессы и превращать данные в знания с помощью искусственного интеллекта.

3. **Feature First** 
4. **Vertical Slice Architecture** 
5. **Boundaries First** 
6. **Dependency Injection** 
7. **Strong Typing**

11. **Event-Driven where justified** 
12. **Idempotency by Design**

### Reliability

16. **Fail Fast / Fail Explicitly** 
17. **Error Handling by Design** 
18. **Database/Data Integrity First** 
19. **Testing by Design** 

### Production

20. **Production First** 
21. **Security First** 
22. **Performance by Design** 
23. **Observability by Default**

Любое изменение должно быть безопасным, измеримым и приносить реальную инженерную пользу.

Не допускаются изменения "ради красоты", смена технологий без объективной выгоды или рефакторинг без архитектурного обоснования.

## Архитектура

- **Feature-First + Vertical Slice** — единственная допустимая архитектура для бэкенда и фронтенда. Каждый функциональный модуль содержит всё необходимое внутри себя: модели, схемы, сервисы, эндпоинты и UI-компоненты.
- **Строгое линейное ветвление** — работаем исключительно в `main`. Параллельные ветки и деревья коммитов запрещены: они порождают путаницу и конфликты. После команды «Принято» — немедленный `git commit` и `git push origin/main`.

## Production by Default

Любой код, создаваемый для Whisperer, считается production-кодом.

Не допускаются:

- временные решения;
- TODO вместо реализации;
- технический долг без явного обоснования;
- "исправим потом";
- демо-решения;
- MVP-подходы;
- экспериментальные архитектурные решения без необходимости.

Каждое изменение должно быть готово к эксплуатации в production сразу после прохождения всех проверок.

# Общие инженерные правила

## Проверка здоровья кода

Проверки здоровья кода запускаются **один раз после завершения задачи**, а не после каждого Write/Edit.

Какую проверку запускать, определяется зоной изменений:

- изменялись только файлы `backend/` → `python-doctor`;
- изменялись только файлы `frontend/` → `react-doctor`;
- изменялись и `backend/`, и `frontend/` → последовательно сначала `python-doctor`, затем `react-doctor`;
- изменения не затрагивают ни `backend/`, ни `frontend/` → проверки не запускаются.

Команды запуска и целевые показатели:

- Backend — раздел «Backend → Инженерные стандарты → Здоровье кода»;
- Frontend — раздел «Frontend → Инженерные стандарты → Здоровье кода».

Проверка автоматизирована хуком `Stop` в `.claude/settings.json`: он определяет затронутые зоны и запускает нужные проверки после завершения задачи. Если хуки отключены, агент обязан выполнить проверки вручную по тем же правилам.

## Промты и инструкции для LLM

**Всё, что читает языковая модель, пишется ИСКЛЮЧИТЕЛЬНО на английском языке.**

Причина не в эстетике. Инструкция на русском — это языковой сигнал: модель принимает его за указание отвечать по-русски. Английский пользователь получает русские вкрапления, а поведение агента начинает зависеть от языка инструкции, а не от языка собеседника. Слабые модели вдобавок соблюдают английскую инструкцию точнее.

### Что считается промтом

Шире, чем принято думать. Правило распространяется на:

- системные инструкции всех каналов и ролей;
- `name` и `description` каждого инструмента;
- `description` каждого параметра и значения `enum`;
- **то, что инструмент ВОЗВРАЩАЕТ** — модель читает результат вызова так же, как промт, и пересказывает его пользователю (метки, статусы, подсказки внутри ответа);
- тексты ошибок, возвращаемых модели;
- служебные маркеры, которые сервер подставляет в тред;
- инструкции MCP-сервера — их читает LLM внешнего клиента;
- промты вспомогательных моделей (зрение, расшифровка, перевод, mind-map, генерация описаний каталога).

Пункт про возвращаемое значение — самый упускаемый: однажды схемы инструментов уже перевели и закрыли тестом, а `list_platform_models` продолжал отдавать модели `kind="чат"` и подсказку по-русски.

### Что остаётся на русском

- комментарии и докстринги — они для инженера, а не для модели;
- логи;
- сообщения пользователю (интерфейс, письма, ошибки HTTP) — они идут через i18n на языке пользователя, см. `i18n.translate_user`;
- русские элементы МНОГОЯЗЫЧНЫХ списков (ключевые слова, распознавание согласия): русский там — один из 16 языков платформы, а не единственный.

### Язык инструкции ≠ язык вывода

Это разные вещи. Промт всегда английский, а на каком языке модель должна ОТВЕЧАТЬ — отдельное продуктовое решение, и оно формулируется в промте явно (`«write IN RUSSIAN»`, `«answer in the language of the user's latest message»`).

Названия языков на них самих (`Русский`, `日本語`) — законное **значение**, а не инструкция: они симметричны для всех локалей и именно так сообщают модели целевой язык. Наивный греп по кириллице захочет их «исправить» — нельзя.

### Ни одна ветка логики не зависит от языка

Списки ключевых слов, регулярные выражения по словам, сравнения с литералами вроде «да»/«нет» обязаны покрывать все 16 языков платформы либо не существовать. Иначе возможности агента фактически различаются по языку собеседника: так «запомни» работало только у русских и англичан, а согласие голосом распознавалось хуже у японцев.

### Проверка

Правило машинное, а не на честном слове:`tests/test_answer_language_unit.py::test_model_facing_instructions_are_english_only`. **Новый промт добавляется в список `_MODEL_FACING` этого теста в том же коммите.** Список заполняется руками, и именно поэтому однажды 83 русских описания инструментов жили при зелёных тестах — в нём не было ни одной строки агента.

## Configuration

Вся конфигурация проекта должна поступать исключительно из переменных окружения.

Запрещается:

- хранить конфигурацию внутри исходного кода;

Любая новая конфигурация должна быть документирована и иметь понятное назначение.

## Совместимость

Запрещается изменять публичные API, события, контракты и модели данных без явной необходимости и плана миграции.

Любые изменения должны сохранять обратную совместимость либо сопровождаться безопасной стратегией миграции.

## Работа с зависимостями

Используются только стабильные версии библиотек.

Перед обновлением любой major/minor версии необходимо:

- изучить changelog;
- проверить breaking changes;
- убедиться в совместимости зависимостей;
- выполнить полное тестирование.

Запрещается обновлять зависимости "до последней версии" без архитектурного анализа.

Перед добавлением новой библиотеки необходимо убедиться, что аналогичная функциональность уже не реализована существующими зависимостями проекта.

# Git Workflow

Whisperer использует линейную модель разработки.

Обязательно соблюдать следующие правила:

- коммиты выполняются только после получения команды **«Принято»**;
- запрещается выполнять автоматические коммиты без явного разрешения пользователя;
- запрещается автоматически создавать новые ветки Git;
- вся работа выполняется в текущей рабочей ветке пользователя;
- одна логически завершённая задача — один атомарный коммит;
- не объединять несколько независимых изменений в один коммит.

## Отправка в origin/main обязательна

**Коммит считается сделанным только после `git push origin main`.** Локальной ветки, живущей отдельно от `origin/main`, у проекта нет и быть не должно: по завершении задачи локальная `main` обязана совпадать с удалённой.

Причина не в аккуратности, а в том, что прод собирается ИЗ РАБОЧЕГО ДЕРЕВА, а не из GitHub. Неотправленный коммит означает, что на боевом сервере работает код, которого в репозитории нет вовсе: восстановить его после потери машины нечем, и «откатиться к тому, что на GitHub» означает откатиться на неизвестное число дней назад. Так и вышло 2026-08-23 — прод ушёл вперёд удалённого репозитория на 30 коммитов и четыре дня, и заметил это не инженер, а владелец.

Порядок в конце задачи:

```
git commit --only <пути>          # см. правило про параллельные сессии ниже
git push origin main
git status -sb                    # ожидается «## main...origin/main» без ahead
```

Отправка идёт **сразу после коммита**, а не «в конце дня»: чем дольше ветки расходятся, тем больше чужой работы уедет одним махом вместе со своей.

`--force` и `--force-with-lease` в `main` запрещены: история линейная и общая, переписать её значит стереть чужие коммиты, которых у переписывающего нет.

Если `push` отклонён (кто-то отправил раньше) — `git pull --rebase origin main` и повторить. Мержить нельзя: модель разработки линейная.

**Коммитить только своими путями.** `git commit -a` и `git add .` запрещены: в рабочем дереве одновременно живут правки параллельных сессий, и «закоммитить всё» означает отправить чужую незавершённую работу. Пути перечисляются явно: `git commit --only <путь> …`.

# Docker Hygiene

При работе с Docker необходимо поддерживать чистую и аккуратную среду разработки, не допуская накопления устаревших контейнеров, образов, сетей и build cache.

Главный принцип — соблюдать золотую середину между чистотой среды и возможностью быстрого отката.

Обязательно соблюдать следующие правила:

- не удалять Docker-ресурсы без понимания, используются ли они проектом;
- не выполнять агрессивную очистку (`docker system prune -a`, удаление всех образов, томов и т.п.) без явной необходимости;
- перед удалением убедиться, что ресурс действительно больше не используется и не потребуется для быстрого отката;
- после успешной миграции или рефакторинга удалять только устаревшие и гарантированно неиспользуемые контейнеры, dangling-образы, сети и build cache;
- сохранять возможность быстро вернуться к предыдущей стабильной версии проекта;
- поддерживать Docker-окружение аккуратным, предсказуемым и удобным для дальнейшей разработки.
