# Interface languages

The user panel (`/app`) speaks 16 languages (`src/lib/language.ts`); the admin panel (`/admin`) is written
in Russian only. Translations use [`use-intl`](https://next-intl.dev/docs/environments/core-library), the core of
next-intl ([ADR 0021](../../docs/adr/0021-public-site-on-nextjs-cabinet-on-vite.md)), without the language in the URL.
How the words themselves are chosen is in `src/i18n/GLOSSARY.md`.

## How a page gets its language

1. Before the first paint, the boot script in `index.html` (`src/i18n/boot-language.ts`) resolves the language
   — Russian on `/admin`, otherwise the `ui_language` cookie, otherwise English — sets `<html lang dir>`
   (`dir="rtl"` for Arabic) and starts downloading that language's catalogue.
2. The build merges every namespace of a language over English into one file with a content hash
   (`tooling/i18n-catalogues.ts`); a gap in a translation shows the English text, never a key.
3. The root route's loader (`src/app/root/root-loader.ts`) resolves the language by the same rule
   (`resolveLocale`) and awaits its catalogue on every navigation, so the next page renders wholly in its
   language: a move between the panels swaps the language in place, without a reload.
4. `I18nProvider` hands messages, formats and the cabinet's time zone to components and the direction to Radix
   (`DirectionProvider`).
5. Picking a language in the user menu (`useSwitchLanguage`) writes the cookie and revalidates the routes: the
   new catalogue loads and the page re-renders in place. Nothing reloads.

## Writing a string

- Put it in the slice's namespace: `src/i18n/messages/en/<namespace>.json`, then the same key in every
  other language. New namespace: create the English file and list it in `src/i18n/namespaces.ts`.
- Components: `const t = useTranslations("kanban")` from `use-intl`. The development mocks word their errors with
  `getTranslations("kanbanApi")` from `src/mocks/runtime.ts`.
- Keys are typed from the English catalogs, and so are their ICU arguments: `t("cleared", { count })` fails
  type-checking without `count`. The declarations (`*.d.json.ts`) are generated by `tooling/message-types.ts`
  in `npm run dev` and `npm run build`; `npm run typecheck` generates them first.
- Plurals, selects and rich text are ICU messages, never code:
  `"cleared": "{count, plural, one {Cleared # task} other {Cleared # tasks}}"` and
  `t.rich("terms", { link: (chunks) => <Link href="/terms">{chunks}</Link> })`.
- Domain code (`domain/`) stays free of use-intl: it returns codes and numbers; the UI turns them into words.
- Data values shown as labels (`"High"`, `"Archive"`) get a key per value: `t(\`priority.${priority}\`)`.
- Keys are camelCase; a key that mirrors an API code may keep its snake_case (`leoActions.web_search`).
- Shared words live in `common` (Cancel, Undo, Rename…, Copy link, "Actions for {name}"); reuse them.
- Admin-only text (the admin panel is Russian only) stays in code, in files listed in
  `ADMIN_ONLY_SOURCES` (`src/scripts/i18n/localized-sources.ts`), e.g. the admin sidebar. Shared chrome that
  both panels show comes from the catalogs and so is Russian in `/admin` through the `ru` catalog.

## Dates, numbers, units

- Always through the formatter: `useFormatter()` (`format.dateTime`, `format.number`,
  `format.relativeTime`, `format.list`), or ICU arguments. Named formats live in `src/i18n/formats.ts`.
- Never `toLocaleString()`, `"en-US"`, or date-fns `format` / `formatDistance*` for display.
- Time zone: the cabinet's zone (`src/i18n/time-zone.ts`) is the person's from `GET /v1/me` (`timezone`), and
  the browser's when the profile has none or names one the browser does not know. The identity session sets it
  when the profile loads; `I18nProvider` gives it to the formatter, so a moment needs no `timeZone` of its own.
  Code outside React reads `cabinetTimeZone()`; the header clock subscribes with `subscribeTimeZone`.
- Calendar days are counted in that zone with `src/i18n/calendar-days.ts`: `dayIn(moment, zone)` is the moment's
  day ("2026-10-20"), `dayOf(value, zone)` takes a day or a moment, `daysBetween(from, to)` counts days and
  `hourIn` names the hour of a greeting. Domain functions take the zone as a parameter; never use a date-fns day
  function (`isToday`, `differenceInCalendarDays`, `startOfDay`…) on a moment, as it counts in the browser's zone.
- A value that is itself a calendar day, not a moment — a due date, an invoice date, a card's expiry, a renewal
  day, a month, a sample time of day — is stored as UTC midnight and formatted with `CALENDAR_DAY`
  (`{ timeZone: "UTC" }`), so it keeps its day in every zone. A date picker's cells are local days: read them
  with the local getters (`dayKey`), not through the zone.
- Two exceptions keep their own zone: the calendar (FullCalendar's grid and its event labels stay on the
  browser's local time until the calendar slice moves to its API) and the admin panel, whose dates are UTC like
  the server's day totals it shows.
- Sizes and durations: `formatBytes(locale, bytes)` and `formatDuration(locale, ms)` from
  `src/i18n/format-units.ts` ("3.2 MB" / "3,2 МБ", "4.2 sec" / "4,2 с" / "4.2 秒").
- Libraries with their own locale (FullCalendar, react-day-picker) get the interface language and direction:
  `useDateFnsLocale()` (`src/i18n/use-date-fns-locale.ts`) loads the date-fns locale, and `dir` comes from `useDirection()`.

## Right to left

- Logical utilities only: `ms-`/`me-`, `ps-`/`pe-`, `start-`/`end-`, `text-start`/`text-end`, `border-s`/`border-e`,
  `rounded-s`/`rounded-e`. Centring with `left-1/2 -translate-x-1/2` is fine.
- Icons that point a way (arrows, chevrons, reply, external link…) get `rtl:-scale-x-100`.
- Radix `side="left" | "right"` is physical: pick it from `useDirection()`.
- Keyboard arrows follow what the user sees: in RTL, ArrowLeft moves towards the end.
- Text written by people or by Leo goes in an element with `dir="auto"`, so an English answer in an
  Arabic interface still reads left to right.

## Text written by Leo

Leo's answers are written by the model in the answer language (Settings › Leo › Response language;
"Auto" = the interface language, `answerLanguage()` in the `leo` slice). The client sends the interface
language with each request; the server decides. Such text never goes through the catalogs.

## Checks

- The i18n check (`src/scripts/i18n.test.ts`, part of `npm test`; alone: `npm run i18n:check`): every language has exactly English's keys; every message is valid ICU with the
  same arguments, select options and all plural categories of its language; nothing is empty or left in
  English; do-not-translate names survive; glossary "Avoid" words and wrong punctuation are rejected; catalog
  files stay within 200 lines. Source listed in `src/scripts/i18n/localized-sources.ts` must have no
  hardcoded copy, physical classes, fixed locales or unmirrored arrows (`i18n-ignore: <reason>` skips a line).
- `npm run i18n:rtl-smoke -- --base <url> [--out <dir>]`: opens the key screens in Arabic in Chromium,
  checks direction and sideways scrolling, keeps `/admin` Russian, and runs the interactive scenarios in
  `src/scripts/rtl-smoke/`.
- `npm test` covers the rules themselves (`src/scripts/i18n/*.test.ts`) and the locale resolution.
