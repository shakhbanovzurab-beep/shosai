# Frontend architecture

The cabinet is a Vite single-page app ([ADR 0021](../../docs/adr/0021-public-site-on-nextjs-cabinet-on-vite.md)):
feature-first vertical slices, with Clean Architecture layers inside each slice. The rules below are checked by
`src/scripts/architecture.test.ts`, which runs in `npm test`.

## Top level

```
index.html      noindex, the pre-paint boot scripts (generated by tooling/boot-script.ts), #root
vite.config.ts  React with React Compiler, Tailwind, base /app/, dev proxy for `npm run dev:api`
tooling/        Build plugins: message catalogues, message types, boot scripts, cabinet paths, mock worker
public/         Favicon, web app manifest and icons (served under /app/)
src/
  main.tsx      Entry: starts the mocks in `npm run dev`, creates the router, renders
  app/          Routing only: route tables, layouts, page modules, redirects, error pages, page metadata
  features/     Vertical slices, one per business capability (see the catalogue below)
  mocks/        Development and test mocks of the API (MSW): runtime, registry, worker start
  components/   Shared UI with no business knowledge: ui/ (shadcn), calendar/ (vendored), feedback, menus…
  hooks/        Shared generic React hooks
  lib/          Shared business-agnostic code: navigation, the data layer (lib/api), cookies, formatting
  i18n/         Interface languages: catalogue loading, provider, message catalogs, glossary (docs/i18n.md)
  config/       App-wide configuration
  styles/       Theme presets, fonts, preferences
  scripts/      Repository checks run as tests (architecture, i18n) and the theme preset generator
```

Code goes into the shared layer only when it is generic (knows nothing about a business capability) and is
used by more than one slice. Shared code never imports from `features/` or `app/`.

## A slice

```
features/<slice>/
  domain/   The business core: API contract types, rules, validation schemas, pure formatting
  data/     Static sample data that screens show until the slice's API exists
  api/      Browser gateway: typed calls to the API through src/lib/api
  model/    Client application layer: stores, resources, use-case actions, hooks
  ui/       React components
  mocks/    The slice's sample API for development and tests (MSW handlers and in-memory stores)
```

A slice has only the folders it needs. Files inside a slice import each other with relative paths.

**No barrel files (F2-D4).** There is no `index.ts`; code imports the module that defines a symbol, by its
path (`@/features/notes/ui/note-detail`). No module re-exports another (`export … from` is a violation). Route
tables import page modules by path, so every page stays a chunk of its own.

### Layers

| Layer    | May import (same slice)          | Must not import                                                        |
| -------- | -------------------------------- | ---------------------------------------------------------------------- |
| `domain` | `domain`                         | React, router, stores, toasts, icons, UI, HTTP, other slices           |
| `data`   | `domain`, `data`                 | the same as `domain`                                                   |
| `api`    | `domain`, `api`                  | React, router, stores, UI (HTTP through `@/lib/api/*` is its job)      |
| `model`  | `domain`, `data`, `api`, `model` | `ui`, UI components                                                    |
| `ui`     | `domain`, `data`, `model`, `ui`  | `api` (go through `model`)                                             |
| `mocks`  | `domain`, `data`, `mocks`        | —                                                                      |

- Between slices: `model`, `ui` and `mocks` may import another slice's modules; `domain`, `data` and `api` may
  not. Slices depend on each other in one direction only: a cycle fails the check.
- Only the mocks (`features/*/mocks`, `src/mocks`) and tests import `mocks/` or `msw`; a production build has
  no mocks (`tooling/check-dist.ts`).
- Only `src/app/`, `src/main.tsx` and `src/mocks/` import `src/app/`.
- No `next`, `next-intl`, `next-themes` import anywhere.
- Every hand-written source file is at most 200 lines; generated files (`generated/` or `@generated` in the
  first five lines) are exempt.

## Routing

React Router in data mode. `src/app/routes/` holds one table per area — user panel, workspace, admin panel,
standalone pages — plus `redirects.ts` for old addresses inside the cabinet. A slice adds its pages there with
a small edit:

- `page(() => import("../pages/user/notes"))` — a page module exporting `Component`, loaded on first visit;
- `pageWithData(loader, component)` — a page whose data loads before it shows: its `loader` module and its
  component module are separate chunks loaded in parallel, so the request never waits for the page's code.

Page modules (`src/app/pages/**`) stay small: `PageMeta` (title and description), query parsing through
`@/lib/navigation`, and the slice's screen. Slices navigate only through `@/lib/navigation` (`Link`,
`useRouter`, `usePathname`, `useSearchParams`, `useParams`).

The root route loads the page's language before rendering (the admin panel is Russian, the rest follows the
`ui_language` cookie) and holds the providers. A 404 thrown by a loader shows the not-found page; any other
failure shows the failure page, worded in every language from a build-time module.

Addresses outside `/app/` that the cabinet serves — `/app`, `/admin/*`, `/oauth/callback`, `/unauthorized` —
are listed in `tooling/cabinet-paths.ts`; the edge serves `index.html` for them (F4).

## Data

`src/lib/api/`:

- `generated/schema.d.ts` — types generated from `backend/openapi.json` by `npm run api:types`;
  `tooling/api-types.test.ts` fails when they are stale;
- `client.ts` — the typed client (`createApiClient`, `dataOf`) for the backend's `/v1` endpoints;
- `request.ts` — `apiRequest` and `jsonBody` for the sample `/api/*` paths the slices still call;
- `errors.ts` — `ApiError` read from the error envelope of ADR 0008 or a legacy `{ detail }`;
- `query-client.ts` — the TanStack Query client: queries retry transient failures, mutations never retry.

Until a slice publishes its endpoints, its screens call the sample paths documented in `docs/<slice>-api.md`,
which `features/<slice>/mocks/` answers in `npm run dev` and in tests. When the slice delivers its API, it
switches its `api/` to the generated client and deletes its mocks, its registry entry in
`src/mocks/handlers.ts` and its `docs/<slice>-api.md`.

### Personal and workspaces

One account works in Personal (its own tools) and in any number of workspaces. Objects are never copied
between them; see `workspace-api.md` for the model.

- `notes` doesn't know about workspaces: the page `src/app/pages/user/note.tsx` composes the note with the
  workspace's share button and its live tasks, passed in through `NoteDetail` props.
- `workspace` doesn't know about File Manager: its "Share from my files" dialog takes the list of files as a
  `picker` slot, which the workspace pages fill with File Manager's `WorkspaceFilePicker`.
- `knowledge-base` reads the account's files from File Manager, so a file is never listed from two stores.
- `shell` picks the sidebar from the URL (`/app/w/{slug}` is a workspace, the rest is Personal) and gives Leo
  the current context.

## Known exception

`src/lib/preferences/theme.ts` holds the theme preset list for the `preferences` slice but stays in
`src/lib/`: `npm run generate:presets` writes it and the pre-commit hook stages it at that path.

Message catalogs are owned by slices (one namespace per slice) but live together in
`src/i18n/messages/<language>/<namespace>.json`: the build merges them into one file per language.

## Adding a feature

1. Create `src/features/<slice>/` with the layers it needs, starting from `domain/` types.
2. Add its page modules under `src/app/pages/` and their routes in `src/app/routes/`, and the navigation entry
   in the `shell` slice.
3. Run `npm test`: the architecture, i18n and API-types checks are tests.
