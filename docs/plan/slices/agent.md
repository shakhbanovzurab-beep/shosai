# agent — slice plan

Prompt: [prompts/S-feature-slice.md](../prompts/S-feature-slice.md), launched through [BACKEND-next-step.md](../prompts/BACKEND-next-step.md). Status: [STATUS.md](../STATUS.md), row `agent`. Slice card: [SLICE_MAP.md §4.2.14–18](../SLICE_MAP.md#1418-leo-agent-decisions-memory-proactive-errands). Design, normative: [Leo architecture](../../design/leo/ARCHITECTURE.md) with ADR 0023–0033 and [ADR 0068](../../adr/0068-leo-agent-slice.md). Cabinet feature: `leo` (SLICE_MAP §4.3), plus Settings › Leo (`settings/ui/leo`), the home's "Needs you" (`leo/ui/needs-you.tsx`, shown by `productivity`) and Studio's skills dialog (`studio`).

`agent` is Leo's core. It holds the person's conversations with Leo in Personal and in each workspace, and runs each turn: it reads through the tools of every slice under the one access policy, names its sources and the space each comes from, and changes nothing except through the Action Gateway, after the person approves a card that says exactly what will change. It also owns Settings › Leo, the feedback on answers, the skills store, the native model proxy of the shipped desktop clients and Leo in the admin panel. The Decision Layer, memory, initiative, errands, voice and MCP are other slices built on its ports (§3.7).

- **Status:** written on 2026-10-23; **approved by the owner on 2026-10-23 with amendments** ([ADR 0068](../../adr/0068-leo-agent-slice.md)): AG-D1, AG-D2, AG-D4, AG-D5, AG-D7, AG-D8 and AG-D11 as written; AG-D3, AG-D6 and AG-D10 amended by the owner; **AG-D12 decided by the owner the same day: turns run in worker processes of a dedicated `agent` queue, the API only streams them** (§2.1), which replaces AG-D9 by the agent workers' grace; AG-D13 (feedback on answers) and AG-D14 (LangGraph's boundary) added by the owner; the cabinet's panel moved to right after step 6 and its cards to right after the cards' backend step (§4). AG-R1 and AG-R2 (§0) are kept as written. The documents of §5 were amended with the approval.
- **Dependencies:** identity is `done`; workspaces·core (steps 1–5) is `done`; billing·entitlements (steps 1–7: `Entitlements`, `TokenAllowanceReader`, Leo's `account` tools) is `done`; notes' read tools (step 14) are `done`; F6 is `done` — the provider port with streaming, cost rows per effect key, breakers per model, two interactive streams per user, input caps, `decide`, and the tool contract `core/agent_tools` (step 9a). Not needed to start: `decisions`, `memory`, `studio`, `knowledge`, `hubs`. The agent runs their documented fallbacks behind ports they bind later (AG-D4, AG-D7). Steps 18–20 wait for studio, knowledge and hubs.
- **Philosophy check:** Leo is where the person asks instead of searching. One conversation follows them across devices, reads what they may read in every space and says where each fact came from, so they never re-explain context or verify blindly. Leo does nothing behind their back: every change is a card with the server's account of its exact targets, approved once and executed once. It stays quiet: nothing of the conversation lives in the browser, a dropped connection resumes where it stopped, a failure is one plain line with a retry, never an error pasted into the conversation, and a rating is one press with no form to fill.

### 1.3 Design point

From Leo §2.4 and §12, at 10 000 DAU (100 000 in brackets): 4 000 Leo users a day; 50 000 turns a day (500 000); 2.9 turns/s at peak (29); ≈ 35 concurrent runs (≈ 350) — one agent worker at 48 runs each (≈ 8), with N+2 reserve (AG-D12). Rows a day: ≈ 150 000 messages (≈ 225 MB), ≈ 50 000 runs, ≤ 75 000 stored tool results (digested over budget), a few thousand actions and audit rows, ratings on a few percent of answers. A turn costs 2 transactions on the hot path plus 1 per approval; ≈ 60 transactions/s at 100 000 DAU fit the Russian home's pools. Valkey holds leases, checkpoints and event logs of active runs: ≈ 350 × 250 KB ≈ 90 MB at 100 000 DAU. The native proxy is a fallback of the desktop clients and adds little load; it shares the per-user caps. Platform budget per turn ≈ 350 ms for EU users (Leo §12), + 3 × 45 ms for Russian users.

### 2.1 AG-D12: where turns run — decided: B

Leo §12 ran a turn inside the API process that received it. The owner asked for the alternative — a turn run by a separate role on the pattern of the workers, the API only serving the stream from the run's Valkey log — compared on releases, memory, scaling and the latency of `run.started`.

| | **A. In the API process** (Leo §12, the plan as first written) | **B. On a dedicated `agent` queue served by its own worker processes** |
|---|---|---|
| Path of a turn | The API admits, commits, sends `run.started` and runs the graph as a detached task of its own process; the events go to the run's Valkey log; the response tails it | The API admits, commits, sends `run.started` and enqueues the run on the `agent` queue; an agent worker runs the graph and writes the events to the log; the API only tails it. An approval enqueues the epilogue's resume the same way |
| Releases | The API's stop grace covers the longest turn (AG-D9: 200 s); each release's old API container lingers with its open streams until its runs end | The API keeps its 30 s: an old API's streams are cut and the cabinet resumes them on the new API from the log (`Last-Event-ID`), the runs untouched. Only agent workers take a 200 s grace and are handed over like the other workers: the new one takes runs before the old one stops. AG-D9 is replaced |
| Memory and CPU | Each API process carries up to 48 runs' state — context, tool results, graph state, streams — ≈ 50–100 MB more, and their CPU and garbage collection run beside the cabinet's requests, whose p95 (nfr-7, 300 ms) then depends on Leo's load | Run state lives in agent workers; an API process holds only idle tails of a few kilobytes each; a runaway run cannot slow or crash the cabinet's API |
| Scaling | Leo's capacity grows only with API processes (48 runs and 64 requests each), each with its pools to both homes | Agent workers scale by concurrent runs (48 each: one at 10 000 DAU, ≈ 8 at 100 000), the API by requests. A global count of running runs in Valkey refuses a turn with 429 `agent_busy` when the fleet is full, instead of letting it wait in the queue |
| `run.started` (L-N2 ≤ 150 ms) | Sent by the API after the commit | The same: sent by the API after the commit, before the enqueue |
| First token | No hop beyond the model | + the queue's pickup (an `XADD` and a blocked `XREADGROUP` on the same Valkey, a few ms) and one Valkey hop per streamed event (A writes the log too, but can also forward events in memory); estimated + 5–15 ms against a model's 0.5–2 s, measured in step 5a |
| What it adds | Drain logic in the API; the stop grace raised | A run task with no automatic retry (a lost run is swept, never re-run); one reader per API process tailing all its streams with one blocked `XREAD`, otherwise a Valkey connection per stream; the global run count; one more process kind in Compose and staging (≈ 250 MB baseline each, with its own pools); amendments to Leo §12 and to the target architecture §4.2 and §5, whose "workers (per queue)" already allows it |

**Decided by the owner on 2026-10-23: B.** Leo is the heaviest and least predictable load in the plane; running it beside the cabinet's requests would couple their latency, their releases and their failures. B costs a few milliseconds before the first token and one more process kind, and fits the process model as it stands. AG-D9 is replaced by the agent workers' grace; ADR 0068, Leo §3.1, §11.1 and §12 and the target architecture §4.2, §5, §12 and §17 record it.

### 3.4 Data (each home)

All tables isolate rows by `user_id` (RLS's personal policy, ADR 0053); none is shareable.

### 3.5 Flows

1. **A turn** (Leo §5.2). Authenticate; admission in Valkey (GCRA per person, the fleet's run count against the agent workers' capacity, ≤ 2 interactive runs per person) and the thread lease (`SET NX PX`; busy → 409, or `supersede` cancels the running one first). One transaction: the person's consent, entitlements snapshot, settings, active memberships and profile (`PrincipalFactory`), the idempotency key, the question and the `agent_runs` row; commit; `run.started`; the run is enqueued on the `agent` queue (AG-D12). An agent worker runs it, writing every event to the run's log; the API's response tails the log through the process's one blocked `XREAD`, so a closed connection or a released API never stops the run. In parallel: the surface's subject digest through its owner's contract, billing's token decision for the tier, attachment digests (step 12) and, later, memory recall. The graph runs `context → model ⇄ tools → propose → respond` within AG-D14's boundary over the provider port, with segment caps (Leo §7.3) and routing (AG-D7). One transaction at the end: the answer, its tool rounds and digests, sources, steps and the run's usage; `run.completed`; the lease released; `agent.turn.completed` through the outbox. After the turn, off the path: the title (the question first, the utility model's words after the first answer) and compaction when the recent segment passes 70% of its cap.
2. **Resume.** `GET /v1/agent/runs/{id}/events` replays the log after `Last-Event-ID` and tails it until the terminal event, from any API process.
3. **A write** (Leo §5.3, §8.4). A write tool call goes to `propose`: the slice's `plan` freezes the targets and `preview` renders them; friction by AG-D7; one transaction stores the action (`proposed`, nonce, expiry 1 h) and its audit row; `action.proposed`, `run.paused`; the checkpoint stays, the lease is released, so the person can go on talking. **Approve** is one conditional `UPDATE … WHERE status = 'proposed' AND nonce = …` (single winner), then each item runs through its slice's `execute` with the key `action_id:index` in the slice's own transaction (`ActionItems.once` writes the key and `agent.action_item.executed` with the effect); outcomes are recorded per item; an item still `executing` past its lease becomes `outcome_unknown` and is never retried. The paused run resumes for its epilogue — a resume task on the `agent` queue — only if the thread is idle and the run is still its latest; otherwise, or when the checkpoint is gone, the outcome is a structured server message in the thread and the run closes `completed` (`checkpoint_lost` or `superseded`). A new turn on a thread closes its paused run the same way; its card stays in "Needs you" until decided or expired. Reject and expiry are single-winner updates with their audit rows.
4. **Cancel, deadlines and failures.** Cancel stops the model stream and closes the run `stopped` with the text so far. The turn deadline (180 s), a 45 s stall or a tool timeout end the run with its code; any unexpected exception ends it `failed` — always exactly one terminal event. A lost agent worker: its leases lapse in 30 s and a sweep every minute marks its `running` runs `failed{process_lost}`, writing the terminal event to their logs; the queue never re-runs them; the question is already stored, so "Retry" answers it. A release (AG-D12): the new agent worker takes runs before the old one gets SIGTERM, and the old one finishes its runs within a 200 s grace; an API process stops within 30 s and its clients resume their streams from the log on another.
5. **Departure** (AG-D3). The membership check hides a workspace's threads at once; `workspaces.member.removed` sets their `erase_after` in the person's scope (ADR 0067); the hourly purge erases those still without an active membership after 7 days and clears the mark of restored ones; `workspaces.workspace.deleted` erases at once. `read_result` refuses a stored result whose spaces the person no longer belongs to.
6. **A rating** (AG-D13). `PUT …/feedback` upserts the answer's rating; in the same transaction, if the person's `improve_models` consent is given and no source of the run is in a workspace, the case is copied (masked) and `shared` set; otherwise any earlier case of the answer is erased. `identity.consent.changed` withdrawing `improve_models` erases the person's cases; a daily purge erases cases older than 12 months.
7. **Account deletion and transfer.** The account data handler exports threads, messages, ratings, settings and skills, erases every row (cases included) and the Valkey keys of the person's runs of the last 24 hours, and copies the rows on a transfer between homes.

### 3.6 Monitors and telemetry

Per `docs/observability.md`. Spans: `agent.run` (root, `run_id` attribute) with `agent.admission`, `agent.context`, `llm.call`, `tool.<name>`, `action.execute`; trace context into the run task (AG-D12), the post-turn tasks and the outbox. Metrics (closed label sets): `shosai_agent_turns_total{channel, outcome}`, `shosai_agent_platform_overhead_seconds`, `shosai_agent_ttft_seconds{tier}`, `shosai_agent_context_tokens{segment}`, `shosai_agent_turn_cost_usd{tier}`, `shosai_agent_tool_calls_total{toolset, effect, outcome}`, `shosai_agent_load_toolset_total`, `shosai_agent_actions_total{origin, outcome}`, `shosai_agent_approval_seconds`, `shosai_agent_active_runs`, `shosai_agent_resumes_total{outcome}`, `shosai_agent_feedback_total{rating, tier, channel}`, `shosai_agent_proxy_requests_total{route, outcome}`, `shosai_agent_queue_pickup_seconds`; the `agent` queue's depth and oldest message age through core's task metrics. Objectives (§16.3): platform overhead ≤ 500 ms p95 for EU users, run platform failures < 1%, approved actions executed or failed with a code within 30 s ≥ 99% — paged, with promtool tests and runbook sections. Invariant monitors (§16.4), hourly per home: an item key executed twice, an item executed without `approved` — both must stay 0 and page. A ticket alert when `load_toolset` passes 5% of turns.

### 3.7 Not in agent

The Decision Layer and Jev (`decisions`, binding AG-D7's ports); long-term memory, the profile core, personalization and Settings › Memory (`memory`); suggestions, the Today feed, `/v1/ws/user` and Web Push (`proactive`); errands and the reminder routes (`errands`); voice turns and in-meeting answers (`capture`, through `VoiceTurns`); Shosai as an MCP server and external MCP tools (`mcp`); search over knowledge (`knowledge`'s `workspace.search`); models, prompts, a prompt's skills and personal context (`studio`, AG-D4, AG-D11); hub containers (`hubs`); team chats' commands (`chats`, through `ChatTurns`); each slice's own tools. ## 6. Risks

- **Our saver for LangGraph.** No maintained Valkey checkpointer stores references only; step 5a writes one against LangGraph's public saver interface and covers it with the crash-injection tests. AG-D14 caps it: if it outgrows one file or needs LangGraph's internals, it goes to the owner as a decision; the pin and the tests catch an interface change.
- **Routing without Jev may miss.** The deterministic rule sends all ready toolsets while they fit, which holds today (22 tools); as slices add toolsets, misses rise until `decisions` binds `turn.route`. `load_toolset`'s rate is measured and alerts above 5%.
- **The provider's stream may stall or cut.** Breakers per model, one retry before the first byte, the 45 s stall rule and the terminal-event guarantee bound the damage; a cut answer is marked, never passed off as complete.
- **Prompt injection through foreign text** (meetings, colleagues' tasks, web pages). No write runs without a card; taint drives friction and egress cards; the safety suite runs in CI. A classifier (`content.injection`) comes with decisions.
- **Valkey is in the path of every turn.** Valkey down → new turns refused (503), approvals still execute from the database (Leo §11.1); the event log and leases are small. The `agent` queue lives there too; its depth, oldest message age and pickup time are watched.
- **The agent workers' hand-over.** A release must start the new agent worker before the old one gets SIGTERM, or turns would wait or be refused for a moment; step 5a adds it to `release.sh` and checks it on staging.
- **Donated conversations hold personal text.** They stay in the person's home, need a consent the person can withdraw at any time, exclude workspace data and attachments' text, are read only by the eval run and by the owner with an audit row, and expire after 12 months.
- **The cabinet's render cost on long answers.** Measured in step 7 against INP and CLS; the incremental renderer is the lever.
- **skills.sh's search API** is not confirmed from its documentation; step 15 confirms it before relying on it, and search fails soft to an empty list.
- **The native proxy's behaviour must stay byte-compatible** with shipped parsers; the D1 gate and the recorded client sequences guard it.
