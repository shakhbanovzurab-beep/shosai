# tasks — slice plan

Prompt: [prompts/S-feature-slice.md](../prompts/S-feature-slice.md), launched through [BACKEND-next-step.md](../prompts/BACKEND-next-step.md). Status: [STATUS.md](../STATUS.md). Slice card: [SLICE_MAP.md §4.2.10](../SLICE_MAP.md#10-tasks). Cabinet feature: `kanban` (SLICE_MAP §4.3), plus the task widgets of `productivity`, `notes` and `workspace`.

`tasks` is the one place a person's work is tracked (SM-3): a task written by hand, an action item a meeting produced, a task a colleague assigned in a workspace, a Jira issue on a synced board and a hub's agreed work are the same kind of row, and a change in any view — a Kanban card, the home's Today list, the workspace's Tasks screen, a meeting's page, Leo — is the same change everywhere. It owns boards with their columns and card order, the placement of tasks on a person's boards, the projection of action items into tasks, workspace tasks under the one access policy, and the two-way Jira sync. It opens wave 2 because hubs, proactive (`tasks.task.*` signals), notes' last native route and the home screen build on it.

- **Status:** written on 2026-10-21; waiting for the owner's approval of TK-D1…TK-D11. **TK-D12 (the golden core) was decided by the owner on 2026-10-21** with the Kanban golden-core plan ([ADR 0060](../../adr/0060-kanban-golden-core.md)).
- **Dependencies:** identity is `done`; workspaces·core (steps 1–5: the access policy, RLS, `resource_grants`, `projects`, `MembershipReader`, the events) is `done`. Not needed to start: workspaces' `WorkspaceMember` dependency (its step 6, blocked on billing's payments) — TK-D1 routes workspace tasks through `/v1/tasks`. Later steps wait, as §4 names: connectors (Jira, steps 12–15), commitments (people, step 16), workspaces' steps 8, 11 and 14a (meeting shares, workspace data, workspace screens). Notes' step 22 (the native action-item route, `meeting_auto_tasks: true`) runs right after this plan's step 5; M2 needs it before the cutover.
- **Philosophy check:** the person never re-enters what a meeting already said: its action items are tasks within a minute of the notes, with the owner and date the meeting named, and they show up where the person already looks — the meeting's page, Today when they are due, the one board they chose for incoming work. Nothing lands on a board uninvited, nothing nags: reminders and "overdue" belong to proactive's budgets. A tick anywhere is a tick everywhere, including Jira. The board keeps only what is open and what was done this month, so it never becomes an archive the person has to tend.

### 1.3 Design point

From §3 of the target architecture: 19 500 meetings a day; at about three action items per meeting (to be measured once notes runs on staging) that is ≈ 60 000 tasks a day from meetings, ≈ 70 000 with hand-made, hub and Leo tasks — ≈ 25 M rows a year across both homes, ≈ 25 GB with indexes. Tasks are mutable and long-lived and are read by owner, workspace, assignee and meeting, never by time range, so the table is not partitioned; partial indexes on open tasks keep the hot reads small. Notes-ready events peak at ≈ 1.6/s (5 850 runs in the peak hour), each one reconcile transaction. A board read is one transaction of ≤ 1 000 open cards; Today and a workspace's list are one page. Jira: one sweep per link every 15 minutes through due rows, webhooks first.

### 3.5 Flows

1. **Action items** (`notes.meeting.notes_ready`, at-least-once): read the meeting's findings through `MeetingFindings` as its owner; in one transaction with the meeting's scope, under the set row's lock: a run already applied → nothing; a touched set → nothing; otherwise the set's tasks are replaced by one task per action item, keyed `(meeting, finding)`, and the set records the run. A person's change to any task of the set stamps `touched_at` in its transaction. `notes.meeting.deleted` deletes the untouched open tasks and stamps `meeting_gone_at`; `.restored` re-runs the projection. `workspaces.meeting.shared` moves the set's personal tasks into the workspace (assignees matched; level `owner`, the parent and named-reader rules for everyone else).
2. **Board read:** the board and its columns; its placements joined with tasks under the policy's predicate (unreadable cards skipped), open ones and those done within 30 days; a card whose status no longer matches its column's kind is shown at the top of the first column of its kind and re-placed; on the incoming board, unplaced open incoming tasks land the same way (TK-D4). Re-placements are written in the read's transaction with a revision bump, so the order is stable.
3. **Move:** under the board's row lock, the rank between the target neighbours (rebalance a column only when a key outgrows 48 characters); another kind sets the task's status in the same transaction, opened in the task's workspace scope (RLS writes a workspace's rows only there), with its events.
4. **Jira out** (step 13): read and validate (transaction 1) → call Jira outside any transaction, with the connection's token from connectors → apply locally with the issue's new `updated` (transaction 2); a refusal is 409 with Jira's reason and nothing local changes; a timeout is 503 `jira_unavailable`. A create first commits an intent row, sends the task's id as an issue property, and an unknown outcome is resolved by searching that property before any retry.
5. **Jira in:** a webhook enqueues a pull of that issue; the pull and the sweep take the link's lock, read the issue and apply it only when its `updated` is newer than `remote_updated_at` — so an echo of our own write changes nothing; the sweep reads `updated >= watermark − 2 min ORDER BY updated ASC` in the account's zone and advances the watermark only past applied issues.

**Rules**

- **Recurrence (KG-D5, the owner's amendment):** marking a recurring task done creates, in the same transaction, the next task — title, description, priority, assignee, its field values, subtasks unticked, the recurrence moved to it — due on the schedule's first date after its due day that is not before the completer's today in their profile zone (past dates skipped, never counted from the completion day; a range keeps its length; day 29–31 falls on a shorter month's last day), at the top of the first `todo` column of the board the completed one sits on, in the same space; its events are a new task's.
- **Leo's marks (KG-D10):** the action-item projection (TK-D3) sets `leo_fields` for the fields it filled from the finding — the assignee from `owner_name`, the due day from `due_on`, the priority from an additive `FindingFacts.priority` (notes, with step 5); a person's change drops that field; a re-projection of an untouched set writes them anew.
- **Cover:** attaching a PNG, JPEG, WebP or GIF makes a WebP preview ≤ 640 px wide in a background job; `preview_url` is null until then and is re-issued with each read.
- **Access:** subtasks, comments, attachments and field values follow their task (TK-D2) and its account and workspace data specs; a person's stickers leave with their account; derived from KG-D4 and nfr-16 (the plan's, not the owner's): values on workspace tasks that use them stay with those tasks as plain text, number or state name; a removed member's comments stay with the workspace.
- **Storage (KG-D3, the owner's amendment):** attachments count in the task owner's storage (FL-D6). Derived (the plan's): a task that moves into a workspace (TK-D3's shared meeting) moves its attachments' bytes to the workspace's storage in the same transaction. Files provides, additively, the purpose, the workspace reservation for it and the copy of a readable file's object into an attachment that keeps the object until its last holder goes (files plan, built with step 3).
- **Column sums are not served:** the board read carries every card (TK-D5), so the cabinet sums the cards it shows, filtered or not.
- **No notifications** from comments, attachments or subtasks; proactive may use them later. Comment bodies and sticker texts are `task:foreign` (TK-D9) once a Leo tool reads them; the tools of steps 7–8 do not.
- **Draft data (revises TK-D7; the owner's decision, without loss):** a draft column colour becomes the nearest `Color` by hue (the draft's default grey `#94A3B8` becomes none); a board whose project has labels gets a `states` sticker named "Labels" in the owner's profile language, one state per label with its colour mapped the same way, visible; a task's first label by name becomes its value, and the other labels are appended to its description as one last line, "Labels: B, C" in the same language.

## 6. Risks

- **Noise from action items.** If meetings yield many weak action items, the meeting page and the incoming board fill up. Measured in step 18; the freeze rule and opt-in landing bound the damage, and notes' extraction prompt is the lever.
- **Name matching assigns the wrong member** when two people share a name: matching requires exactly one member; otherwise the task stays unassigned with the name shown.
- **The parent and named-reader rules touch workspaces' policy**, the platform's single point of access; they are additive, covered by the isolation kit and the hourly self-test, and reviewed against workspaces' plan.
- **Jira's webhook signature mechanism** is not settled by public documents; step 14 confirms it on a live delivery before relying on it, and the unguessable link id stays as the second check.
- **Atlassian rate limits** under many links: back-off per link, due rows spread by `next_sync_at`, webhooks first.
- **Workspace screens wait** for workspaces' step 14a, which waits for billing's payments: until then workspace tasks are reachable through the API, Leo and the personal widgets only.
